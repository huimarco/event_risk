# event_risk — project context

## What this is
A data product for institutional investors built on prediction-market odds (Kalshi + Polymarket) for geopolitical events. Two value props:

1. **Preserved history that can't be backfilled** — not just prices (venues partially serve those) but order book depth, the full market universe at each point in time (incl. delisted/voided/renamed), contract rule versions, and resolution records.
2. **A point-in-time knowledge graph** linking markets → canonical propositions → entities → securities, with empirically estimated "event betas."

Positioning: risk-measurement infrastructure, not an alpha signal. Consensus numbers are a feature for risk desks; alpha-seekers get raw history to build their own models.

## Current state
- Collection is scoped to **only what the knowledge graph + event betas need** (decision 2026-10-15; the raw-data-product tables — universe events, resolutions, order books, raw payload archive — were dropped). Append-only DuckDB (`schema.sql`; local file or MotherDuck via `DB=md:...`). Free tier only — no paid infra; spotty data is fine as long as `collection_runs` makes gaps visible.
- `collector.py` (GitHub Actions, every 15 min): sweeps Kalshi `KALSHI_CATEGORIES` (default `World,Politics` — China/Taiwan series live under Politics; `World` alone is nearly empty) and Polymarket `POLY_TAGS` (default `geopolitics`). Writes `market_snapshots` (source=`realtime`; bid/ask/last/volume_24h/OI for non-final markets) and `market_versions` (contract terms, new row on hash change).
- `backfill.py` (manual workflow, one-time, re-runnable): hourly history for geopolitical markets (same scope test as the graph), open and settled, volume ≥ `BACKFILL_MIN_VOLUME`, into `market_snapshots` with source=`backfill`. Kalshi candlesticks (5000/request; `/historical/...` for markets settled before Kalshi's cutoff); Polymarket `/prices-history` (≤15-day windows; price only, no bid/ask/OI).
- `securities.py` (manual, quarterly): merges S&P 500 constituents from Wikipedia's list into `securities.csv` (sector, sub-industry, HQ, issuer Wikidata QID; Yahoo symbols BRK.B→BRK-B); keeps hand-written rows, clears `index` for leavers. 543 securities as of 2026-10-17. `seeds/exposures.csv` was expanded once (2026-10-17) with 587 rule-generated rows (`rationale` = `rule: <GICS sub-industry>` or HQ country) → 684 rows covering 213 of 543 securities; financials/REITs/software/health services intentionally have none. Rules are analyst priors, editable like any row; algorithmic exposures (issuer QIDs → Wikipedia relatedness) are deferred by decision.
- `prices.py` (daily workflow): daily close/adj close for `securities.csv` from Yahoo Finance's unofficial chart API into `security_prices`. Research only — not licensed; replace before selling betas.
- Views: `v_market_prob` (mid if spread ≤ 0.10 else last), `v_market_latest`.
- Scope test runs right after the cheap entity pass (`entities.discover`: title lookup + Wikidata), before relatedness, so out-of-scope markets cost no co-occurrence queries. Refresh cached facts manually: `python graph_build.py --refresh wikidata` (monthly) / `--refresh relatedness` (yearly) or the `refresh` workflow; refresh appends, latest wins, and forces a rebuild.
- GitHub Actions workflows (renamed 2026-10-17): `collect_markets_and_update_graph` (15-min cron: collector.py then graph_build.py), `get_security_prices` (weekdays), `backfill_market_history` (manual), `refresh_wikipedia_facts` (manual, input wikidata|relatedness). The graph job and refresh share concurrency group `graph`.
- `graph_build.py` (runs after the collector) **only does work when its inputs change** (decision 2026-10-17): it fingerprints market_versions (count + latest first_seen_at), seed files and the graph code, and skips if unchanged — price snapshots alone never touch the graph. Decisions are point-in-time and reproducible: each market pair is judged as of the newer market's listing (that date + both prices then, via ASOF lookup), markets are processed in a fixed order, pairs compared in key order, and ladders link every pair of rungs (never retract on a new rung). Verified: a new market adds only its own nodes/links; nothing existing is rewritten. It builds the knowledge graph into `graph_nodes` / `graph_edges` — bitemporal, append-only assertions (`op` assert/retract, `valid_from/valid_to` = valid time, `recorded_at` = transaction time); each run writes only the diff. Read through table macros `nodes_asof(valid_at, known_at)` / `edges_asof(...)`.
- **Market → proposition matching is algorithmic** (`matching.py`, decision 2026-10-16): each market is parsed into a contract signature (action from a fixed vocabulary, actor/target entities, time window from the venues' templated rules, threshold, qualifying conditions) and compared field by field → `same_as` (one proposition, blended) / `near_equivalent` / `implies` / rejected-with-reason. Guards: every distinctive word of one question must appear in the other's text; entities compare via top-level parents (Trump→US); windows that differ only in elapsed time, and any `same_as`, must be confirmed by prices within `PRICE_TOLERANCE` (the event may already have happened in the gap — e.g. "Trump visits China in 2026" at 99.95% vs a Kalshi market opened after his May visit at 88.5%). No LLM, no string similarity. Humans override via `seeds/match_overrides.csv` (always wins); `python graph_build.py --review` dumps matches, rejections and unparsed markets as CSV.
- **Entities are regenerated from the markets on every build** (`entities.py`, decision 2026-10-16; no hand-made entity lists or links). Candidate phrases in each question are looked up as Wikipedia titles/redirects (longest match, disambiguation pages skipped; a lone surname like "Xi" resolves to the unique already-linked entity containing it). Wikidata gives type (person = instance of human; country = has ISO code; organisation/place = has a country; else concept) and parent (citizenship for people, country otherwise — used by matching, e.g. Trump→US). Concepts are kept only if specific (< 1% of Wikipedia articles mention them) **and** related (≥ `MIN_RELATEDNESS`) to an actor in the same question.
- Entity ↔ entity edges: typed Wikidata statements (citizen_of, country, head_of_state, part_of, …) plus `related`, all weighted by **normalized co-occurrence on Wikipedia text** (the Normalized Google Distance formula, Cilibrasi & Vitányi 2007; same as Milne–Witten on links): counts of articles mentioning A, B and both via the search API. Prose mentions, not links — navboxes create fake co-citation (WuXi Biologics–TSMC: 332 shared links, 1 shared mention). Requires ≥ `MIN_COOCCURRENCE` (10) shared articles. Scored pairs: co-mentioned in a question, Wikidata-linked, or entity × exposure-entity. Google's own counts aren't used: no free API, and its hit counts are unstable estimates.
- All Wikipedia/Wikidata lookups are cached in MotherDuck `wiki_cache` (append-only, saved per batch). First build ≈ 13 min (~2.4k co-occurrence queries); later builds only fetch new phrases/pairs.
- **Signed impact** (2026-10-18): `involves` edges carry role (actor/target/party/concept), action, channel, weight = severity × role weight and sign = what YES means for the entity (`matching.EFFECTS`; negated questions flip; unknown actions → sign NULL, weight 0.3). Exposure edges carry `channel_signs` from `seeds/channel_signs.csv` (industries that gain from escalation; default +1 = suffers with the entity). `Graph.exposures_of` sums over every path (entity itself, or one linked-entity hop × `LINK_DAMPING` 0.5 × link weight): `impact` (signed sum), `score` (noisy-OR relevance), API adds `risk` = |impact|·√(p(1−p)), `direction`, top paths; scan nets impact across holdings. Units are graph units, not returns.
- `backtest.py` (manual): lasting daily jumps (≥ `--jump`, half the move holds next day) vs security abnormal returns (vs SPY, 2 trading days, z by own SD). Magnitude within each security, direction hit rate, calibration slope. First run 2026-10-18 (62 priced securities): ~12% larger moves on linked-jump days but no gradient with score, direction 49–50% → priors not validated; rerun once the S&P 500 price backfill lands. Comparing linked vs unlinked *securities* is confounded by volatility — don't.
- **Matcher fixes (2026-10-18)** that also corrected live merges: ±1-day window slack only across venues and never for single-day windows (daily ladders were chaining into one proposition); window read from the operative "will resolve to" sentence (news preambles carried a background date); narrower question window wins over event-level rules; numeric thresholds without % ("$80", "20-21 seats", "225+", "N times"); negation (not/ends/lifted, outside parentheses) never matches the plain question; same-venue pairs whose operative rules name things neither question has → near_equivalent; verb only in rules → first-named entity is the actor. New actions: strike, capture/enter, ceasefire, transit, join, sanction_relief, annex, close, reopen, deploy, evacuate, withdraw, criticize, regime_fall, outage, agreement, vote, appear, appoint, plus broader leave_office (unparsed markets 7.4k → 1.4k of 10.9k; cross-venue merges 69 → 101 markets, e.g. Kalshi/Polymarket "head of state of Venezuela" pairs). The matcher's price lookup is batched (`PRICE_LOOKUP_BATCH`): one big ASOF join fails on MotherDuck. `graph_build.group` refuses a same_as union that would put two same-venue markets with different deadlines in one proposition (pairwise ±1-day cross-venue slack chained Polymarket "by Jul 19" and "by Jul 20" via Kalshi "before Jul 21"); the pair becomes near_equivalent. Start-only differences (relisted, price-verified) still merge; curated overrides always merge.
- **Questions** (2026-10-19): market → proposition (one bet, cross-venue) → **question** (`rung_of`). `matching.ladder_key` = signature minus deadline (deadline ladders: "China invades Taiwan by Jun 2026 / Dec 2027" = one question) or, when the signature has a threshold, minus threshold but keeping the measurement window (one question per period: "more than 15/20/25 Hormuz transit calls, week of Oct 19–25"); threshold wording ("fewer", "above"…) is ignored. Same venue + same window + same threshold within a key = different outcomes/rules (e.g. "Person O/P as Iran's head of state") → separate questions. Id/name from the earliest-listed rung (`q:<venue>:<id>`; name = rung text minus date/threshold). Unparsed propositions are single-rung questions. ~4.8k questions (~2k live) from ~10.8k propositions. **Entities (and so securities/exposures) attach only to questions**; logical edges (implies/mutex/near_equivalent) stay between propositions. `matching.parse_window` reads periods ("from Oct 19 to Oct 25", "between March 17-23").

## Data model (target)
**Nodes**
- `market` — venue contract (Kalshi ticker / Polymarket market id)
- `proposition` — venue-agnostic real-world question; probability = liquidity-weighted blend of equivalent markets
- `entity` — country, leader, org, chokepoint, commodity (IDs: ISO codes, Wikidata QIDs, LEI)
- `security` — equity, ETF, future, FX, bond/CDS (IDs: FIGI/ISIN/ticker)

**Edges** (each with sign, weight, confidence, provenance, `valid_from`/`valid_to`, `recorded_at`)
- market → proposition (`same_as` / `near_equivalent`, with resolution-difference note)
- proposition → proposition (logical: implies / mutually exclusive / ladder — deterministic from structure; causal/correlated — proposed, validated by co-movement)
- proposition → entity (`involves`, from entity extraction)
- entity → security (structural exposure: revenue geography, supply chain, domicile, commodity input)
- proposition → security (empirical event beta, shrunk toward structural prior)

Everything bitemporal and append-only so the graph and data can be reconstructed `as_of` any date.

## Methodology
1. **Canonicalization**: embed title + rules, LLM proposes cross-venue matches → human review queue. Don't blend markets whose resolution rules materially differ.
2. **Proposition probability**: single market = cleaned price; multiple equivalent = liquidity/spread-weighted average; ladders allow derived probabilities (e.g. P(between June and Dec) = P(by Dec) − P(by June)). Later: bias adjustment (fees, time value, favorite-longshot) calibrated on resolution history.
3. **Logical edges**: deterministic from date/strike ladders, Polymarket `negRisk`, Kalshi multi-market events.
4. **Entity → security**: reference data; weight = exposure share.
5. **Event beta**: detect probability jumps (e.g. |Δp| > 5pts within 1h, liquidity-filtered) → abnormal returns vs market/sector factor model, or regress returns on Δp with factor controls. Output β, SE, n_events, lag. Bayesian shrinkage toward structural prior (events are rare → noisy).
6. **Storage**: plain `nodes`/`edges` tables in DuckDB/Postgres for MVP; graph DB only if >3-hop queries become routine.

## MVP scope
- Scope (decision 2026-10-17): **all geopolitical markets** — Polymarket `geopolitics` tag, plus Kalshi World/Politics markets involving a foreign state actor (`graph_build.geopolitical`: an actor whose Wikidata country ≠ US). Securities/exposures still cover only the original US–China/Taiwan/semis theme; widening them is open work.
- Products: raw history API, geopolitical beta, portfolio scan.
- Priority: (1) market data for graph + betas (realtime + backfill + security prices — done), (2) propositions + mapping, (3) entities/securities, (4) event beta, (5) API + bulk export. Raw-data-product capture (resolutions, order books, universe history, payload archive) is deferred.

## Long-term plan
- **Second-opinion entity linker**: run an off-the-shelf neural linker (e.g. ReFinED, REL) alongside the Wikipedia title lookup; agreement raises `involves` confidence, disagreement goes to a review queue, its extra finds become candidates. The deterministic linker stays the source of truth (pin and record the model version on any edge it influences).
- Entity linking robustness: anchor-text "commonness" priors (how often a phrase links to each article) and coherence with the question's other entities instead of skipping disambiguation pages; a labelled evaluation set from `--review` / overrides to measure precision and recall.
- Sourced exposures (SEC XBRL revenue by geography, ETF country weights, 10-K supplier disclosures) replacing `exposures.csv`; a small classifier for role/polarity/channel beyond the regex vocabulary.
- Empirical event betas with shrinkage to the structural impact prior, pooled across propositions sharing action family + target; proposition ↔ proposition correlation edges from co-movement (graphical lasso).
- **Monotonicity check on question ladders** (production, not just review): for a deadline ladder, P(by later date) ≥ P(by earlier date); for a ">" threshold ladder in one period, P(> higher) ≤ P(> lower). Violations flag a wrong grouping or mispricing — surface them in a review list / `--review` output and on the question in the API, rather than silently plotting an incoherent curve.
- Bitemporal entity edges from Wikidata start/end qualifiers (head_of_state etc. are currently valid from 2020).

## Open risks
- **Licensing**: check Kalshi & Polymarket terms on commercial redistribution of raw quotes before selling raw data. Derived data (consensus probs, betas, graph) is on firmer ground.
- **Equity price data source** for event betas — needs a properly licensed feed for production.
- **Scheduler**: GitHub Actions is too coarse/unreliable for intraday order book capture; move to a real scheduler or websockets.
- Published betas lose alpha value with adoption — position as risk infrastructure.
